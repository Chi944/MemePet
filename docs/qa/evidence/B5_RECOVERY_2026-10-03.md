## Delivered behavior

- After a wallet returns a hash, store only version, action, chain, registry,
  account and public hash. The stable scope survives refresh and provider changes.
  No signature, key, balance or game progress is stored.
- On reconnect in the same scope, inspect the journal before allowing writes.
  Recovery only reads; it cannot connect, sign, send, fund or switch networks.
- Verify independent RPC chain ID, exact sender/registry/zero value/allowed call,
  transaction and receipt inclusion, then pet facts at the receipt block. Recheck
  the block header and chain after reading facts. Unknown is never confirmed failure.
- Keep unresolved hashes visible and block another adoption or care. A receipt
  with unavailable facts stays awaiting facts; Check status retries only reads.
  Community progress is read independently and never inferred from the pet.
- Read attempts have a 15-second total budget and 4-second HTTP limits. The fresh
  receipt waiter has a 60-second timeout, after which bounded read-only recovery
  determines the visible state. Wallet approval is not given a short RPC deadline.
- Validate replacements independently against the original sender/nonce/call.
  A verified same-call replacement can be followed; a proven zero-value self-send
  cancellation is distinct from success. Different or unverifiable replacements
  remain unresolved. A callback's reason alone is not evidence.
- Account, network and provider changes invalidate old results. Background reads
  cannot publish over a newly discovered journal. Storage errors preserve the hash
  in memory and display a warning; guarded removal cannot erase a different
  observed saved hash.

## Limits and next acceptance

Browser storage can be disabled, cleared, or unavailable. If the page closes
before the wallet returns a hash, there is no saved hash to recover. A public
hash is useful evidence but cannot guarantee finality or network availability.
Storage guards are not an atomic lock across independent browser tabs. If an RPC
forgets an original replaced transaction, recovery remains conservative rather
than inventing cancellation. No expiry enables automatic resubmission.

Before claiming genuine B5 acceptance, identify the deployed source, run a fresh
read-only account preflight, and coordinate one due testnet care with Deston.
Refresh after the returned hash is saved, then verify that the same hash is
recovered without another signature/submission and that the receipt-bound pet,
community read and cooldown settle correctly. Record the actual ordering: a fast
chain may confirm before refresh, which proves confirmed-hash recovery but not
a continuously observed pending-refresh path. Preserve that distinction.

Use no forced failures or replacement transactions on the public network merely
to imitate the simulated scenarios. If no suitable account is due, leave genuine
acceptance open rather than manufacture progress. A playable finale backup and
timed rehearsal remain separate deliverables.
